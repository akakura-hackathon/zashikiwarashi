## 2. デザインルール（アプリ本体と同じトーンにする）

### 2.1 原則（UI_DESIGN_SPEC §1 準拠）

1. **白地・黒文字・細い罫線。** 色は「意味があるときだけ」使う。装飾目的のグラデーション・ネオン・グラスモーフィズムは使わない。
2. **1スライド1メッセージ。** 見出し1行＋要点は最大3つ。
3. **色相は 緑・赤・黄土 の3系統（＋洪水の青）だけ。** これ以上増やさない。
4. **AIっぽい装飾を排除。** ロボット・脳・光る回路・宇宙背景などの定番AIイラストは禁止。生活感のある線画・実画面のスクリーンショットを使う。
5. 影は原則なし。角丸は控えめ（カード 10〜14px、ボタン・ピルは丸）。

### 2.2 カラーパレット

| 役割 | 色 | スライドでの使いどころ |
|---|---|---|
| 背景（標準） | `#FFFFFF` | ほぼ全スライド |
| 背景（キャンバス） | `#F4F4F2` | 図・スクショを載せる面、区切り帯 |
| 本文・見出し | `#1F1F1F` | すべての文字の基本色 |
| 補足文 | `#666666` | 注釈・出典・小見出し |
| 罫線 | `#E8E8E8` | 表・カード枠・区切り線（1px） |
| ブランド緑 | `#2D8680` | 「解決」「肯定」「協力する」、強調語、アクセントバー |
| 緑（淡） | `#58B0A9` / `#E4F2F0` | 進捗・グラフの塗り / 強調ボックスの背景 |
| 危険の赤 | `#C23B2E` | 「課題」「攻撃」「遮断」「緊急」、数字の強調（少量） |
| 注意の黄土 | `#8A5A00` | 「進行中」「要配慮」「注意」 |
| 情報の青 | `#3E6E99` / `#E3EDF6` | 洪水シナリオのみ |
| 暗背景（章扉のみ可） | `#1E2524` ＋ 文字 `#ECECE6` | 表紙・エンディング（ロック画面と同じ色） |

### 2.3 タイポグラフィ

| 用途 | 書体 | サイズ目安（1920×1080） |
|---|---|---|
| 和文・欧文すべて | **Zen Kaku Gothic New**（Google Fonts。400/500/700/900） | — |
| 数字・時刻・部屋番号 | **IBM Plex Mono**（500/600） | — |
| スライド見出し | Zen Kaku Gothic New 900 | 64〜72pt |
| 本文・要点 | Zen Kaku Gothic New 500〜700 | 32〜40pt |
| 注釈 | Zen Kaku Gothic New 500, `#666666` | 20〜24pt |
| ロゴ表記 | 「ZASHIKIWARASHI」900、字間 0.04em。左に緑の角丸四角に白「ざ」 | — |

### 2.4 レイアウト共通

- 余白: 左右 120px、上 96px、下 80px。
- 左上: 小さなロゴ（緑の「ざ」アイコン＋ZASHIKIWARASHI）。右下: スライド番号（IBM Plex Mono, `#666666`）。
- 見出しの上に、章を示す小ラベル（例:「01 課題」）を `#2D8680` で置く。
- 画面録画の上に重ねるテロップ用スライド（S07〜S10）は、**下部 1/4 に白帯（不透明度 92%）＋黒文字** の帯テロップ形式にし、上部は空ける。

### 2.5 素材

- アプリ画面のスクリーンショット: 本番 `https://zashikiwarashi.web.app`（または `http://localhost:3000`）から撮影。左が検証画面（コックピット）、右がスマホ実機フレーム（住民 / 管理人）。
- 構成図: `diagrams/Zashikiwarashi_structure_architecture_ランタイム構成_v1.4.drawio` を draw.io から PNG/SVG 書き出しして使う。
- アイコン: 線画（stroke 1.8 相当、丸端）。Material Symbols Outlined 等で統一。

## 3. ペルソナ・用語の表記統一（画面の最新仕様に合わせる）

| 使う表記 | 使わない表記 |
|---|---|
| **管理人** | 防災センター、管理者 |
| **住民（301号室）** | 住民I、住民 I |
| 302号室の高齢単身世帯（確認先） | 住民H |
| Building Agent（建物全体を調整） | Building Coordinator Agent（初出のみ併記可） |
| Resident Agent（住民ひとりの代理人） | — |
| 段階的開示（Progressive Disclosure） | — |
| Human-in-the-Loop（本人承認） | — |
| 検証画面（左）／スマホ画面（右） | コックピット（初出のみ併記可） |

- 「AIが勝手に〜しない」「LLMに権限を与えない」は本プロダクトの核なので、言い換えずにそのまま使う。
- 住民が他人の安否回答状況を見られる表現は入れない（安否状況は管理人だけが見る）。

## 4. スライド別仕様（14枚・約5分）

時間配分は [DEMO_SPEC.md](DEMO_SPEC.md) §1 のタイムラインに対応。

### 章A: 課題とコンセプト（0:00〜0:45）— 審査基準①

#### S01 表紙（0:00〜0:05）
- 背景: `#1E2524`（ロック画面色）。文字 `#ECECE6`。
- 中央: ロゴ「ざ」アイコン（大）＋ **Zashikiwarashi**
- サブ: **仲良くならなくても、助け合える。**
- 下部小: マンション災害時の Multi-Agent 共助サービス ／ Google Cloud Japan AI Hackathon Vol.5
- ナレーション: なし（BGM のみ）または「Zashikiwarashi です。」

#### S02 課題: マンションの「垂直孤立」（0:05〜0:20）
- ラベル: 01 課題
- 見出し: **エレベーターが止まると、マンションは「縦の孤島」になる。**
- 図: 5階建ての建物断面の線画。EV に赤の × 、高層階に人物アイコン（黄土の枠＝要配慮）。
- 要点（3つ）:
  - 高齢単身世帯は階段で降りられない
  - 管理人1人で50戸の安否確認に **1〜2時間**（数字は IBM Plex Mono・赤）
  - 助けられる住民はいるのに、誰が困っているか分からない
- ナレーション: 「大規模災害でエレベーターが止まると、マンションは縦の孤島になります。公的救助が届くまで、棟内の助け合いが欠かせません。」

#### S03 既存の仕組みが使われない理由（0:20〜0:32）
- 見出し: **「平時の登録」を求めた瞬間、誰も使わなくなる。**
- 3列カード（枠 `#E8E8E8`、見出し赤の小ドット付き）:
  1. 平時のプライバシー懸念 — 在宅状況や持病をグループに晒したくない
  2. 人物評価への抵抗 — 「協力的な人」とスコアされたくない
  3. 善意への過度な依存 — 無理な依頼で共倒れになる
- ナレーション: 「しかし平時からボランティア登録を求めると、プライバシーや人間関係の負担から、誰も登録しません。」

#### S04 コンセプト（0:32〜0:45）
- ラベル: 02 解決
- 見出し: **普段は何もしない。災害のときだけ、Agent が立ち上がる。**
- 中央に2つの大きな原則（緑の左線付きボックス、背景 `#E4F2F0`）:
  - **平時の手入力ゼロ**
  - **人物プロファイリング禁止**
- 下: 「住民ごとの Resident Agent ＋ 建物全体の Building Agent が、個人情報を出さずに『誰が困っていて、誰なら無理なく助けられるか』を見つける」
- ナレーション: 「Zashikiwarashi は、平時の手入力ゼロ・人物プロファイリング禁止を徹底し、災害時だけ自律的に立ち上がる Multi-Agent 防災サービスです。」

### 章B: エージェントの自律協調（0:45〜2:00）— 審査基準②

#### S05 2種類の Agent（0:45〜1:00）
- ラベル: 03 Multi-Agent
- 見出し: **建物を見る Agent と、住民を守る Agent。**
- 左右2カラム図:
  - 左「Building Agent」: 建物全体の最適化／同じ階・近い部屋から確認役を選ぶ／4大災害（地震・停電・火災・洪水）でロジックを切替
  - 右「Resident Agent」: 住民ひとりの代理人／身体の制約に合わない依頼は断り、代わりの案を返す／部屋番号を本人承認まで出さない
  - 中央の矢印に「抽象トークンだけをやり取り（例: 3F_UNIT）」
- ナレーション: 「建物全体を調整する Building Agent と、住民ひとりを守る Resident Agent が、個人情報を出さない抽象的な情報だけでやり取りします。」

#### S06 災害時の流れ（1:00〜1:15）
- 見出し: **発令から優先救助まで、人がやるのは「1タップ」だけ。**
- 横並びタイムライン（ドット: 完了＝`#1F1F1F`、要所＝緑）:
  1. 発令（管理人がワンタップ → 50戸へ安否確認）
  2. 応答（住民が「無事 / 被害あり」を1タップ）
  3. トリアージ（Building Agent が近い「無事」の住民を確認役に選ぶ）
  4. 打診・承認（部屋番号は伏せたまま依頼 → 本人が「協力する」）
  5. 開示・実行（承認した瞬間だけ部屋番号を表示）
  6. 優先救助（「本人未応答 × 隣室も応答なし」を管理人へ最優先表示）
- ナレーション: 「人がすることは、発令・回答・承認・報告の1タップだけ。残りは Agent が自律的に進めます。」

#### S07 デモ①テロップ: 災害発令とトリアージ（1:15〜2:00）※画面録画に重ねる
- 帯テロップ（下部1/4）:
  - 1行目（大）: **管理人のワンタップで、50戸へ安否確認を一斉配信**
  - 2行目（小・緑）: Building Agent（Gemini 2.5 Flash）が同じ階で一番近い「無事」の住民を確認役に選ぶ
- 録画内容: 検証画面で「地震」→ 発令、住民（301号室）が「無事」、「トリアージ」実行 → 「隣室確認の状況」に担当と確認先が出る。
- 発令時刻は画面上の実時刻（固定の「8:03」ではない）が映ることを確認する。

### 章C: プライバシーと本人承認（2:00〜3:15）— 審査基準②③

#### S08 段階的開示の説明（2:00〜2:20）
- ラベル: 04 Progressive Disclosure
- 見出し: **部屋番号は、本人が「協力する」と押した瞬間だけ。**
- 3段階の図（左→右、段ごとに情報が細かくなる）:
  - 抽象「対応できる住民が1名います」
  - 条件「同じ3階の未応答のお宅です」
  - 識別「**302** 号室」（IBM Plex Mono 大・本人承認後のみ）
- 段の間に鍵アイコン、最後の段の前に「本人承認（Human-in-the-Loop）」の緑ピル。
- ナレーション: 「依頼が届いた時点では、相手の部屋番号は伏せられています。住民が自分の意思で協力すると押した瞬間にだけ、コードが部屋番号を開示します。」

#### S09 デモ②テロップ: 住民スマホ体験（2:20〜3:00）※画面録画に重ねる
- 帯テロップ:
  - 1行目: **承認前は「3階の未応答のお宅」— 承認した瞬間に「302号室」**
  - 2行目（小）: 断っても理由は聞かれない。評価にも残らない。
- 録画内容: 住民（301号室）のスマホに依頼着信 → 伏せ字 → 「協力する」→ 部屋番号表示 → 「応答がなかった」を報告。

#### S10 デモ②’テロップ: 管理人スマホ（3:00〜3:15）※画面録画に重ねる
- 帯テロップ:
  - 1行目: **管理人は50戸ではなく、数戸だけに向かえばよい**
  - 2行目（小・赤）: 「本人未応答 × 隣室も応答なし」を最優先アラートで表示
- 録画内容: 管理人スマホに切替 → 「隣室確認の状況」の要対応先頭と最優先アラート。

### 章D: ガバナンスと実装（3:15〜5:00）— 審査基準③

#### S11 LLM に権限を与えない（3:15〜3:35）
- ラベル: 05 Governance
- 見出し: **AI の善意に頼らない。守るのはコード。**
- 3層の防御図（上から下に、各層に「遮断」の赤ラベル）:
  - Model Armor（入力）— プロンプトインジェクションを Agent に届く前に遮断（HTTP 400）
  - Agent Gateway ＋ IAP ポリシー — 権限外のツール呼び出しを拒否
  - Policy Engine（コード）— 未承認アクション・部屋番号の書き込み／開示を遮断
- 下注: 協力・拒否の履歴は監査ログのみ。スコアや評価には変換しない。
- ナレーション: 「命とプライバシーを扱うからこそ、AI の善意やプロンプトには頼りません。アクセス権と開示の可否は、すべてコードと Google Cloud のガバナンス機能で強制します。」

#### S12 デモ③テロップ: 攻撃遮断（3:35〜4:15）※画面録画に重ねる
- 帯テロップ:
  - 1行目: **プロンプトインジェクションを、Model Armor が実機で遮断**
  - 2行目（小）: 権限外ツール呼び出し拒否（IAP CEL）／部屋番号の外部漏洩遮断（SDP）も検証可能
- 録画内容: 「Agentガバナンス検証」→ 攻撃テスト実行 → ログに遮断結果。

#### S13 アーキテクチャ（4:15〜4:40）
- ラベル: 06 Architecture
- 見出し: **Google Cloud 単一環境で、すべて本番稼働。**
- 図: `ランタイム構成_v1.4.drawio` の書き出し画像を全面に配置（背景 `#F4F4F2`、余白多め）。
- 右側または下部に技術スタックのチップ（枠 `#E8E8E8`、文字 `#1F1F1F`）:
  Next.js 15 / Firebase Hosting ／ API Gateway ／ Cloud Run（FastAPI: api・tools）／ Google ADK ＋ Gemini 2.5 Flash ／ Agent Gateway ・ Model Armor ／ Cloud Firestore ／ Cloud Logging ・ Cloud Trace ／ Terraform ・ GitHub Actions（Workload Identity Federation）
- 書かないもの: Pub/Sub、BigQuery（使っていない）。
- ナレーション: 「フロントからエージェント、ガバナンス、データまで、すべて Google Cloud の単一環境に Terraform で構築し、実際に稼働させています。」

#### S14 エンディング（4:40〜5:00）
- 背景: `#1E2524`、文字 `#ECECE6`。
- 中央: **普段は意識しなくていい。必要なときだけ、マンション全体がセーフティネットになる。**
- 下: ロゴ ＋ `https://zashikiwarashi.web.app`（IBM Plex Mono）
- 小さく今後の拡張: オフライン PWA ／ BLE メッシュでの安否リレー ／ スマートロック連携
- ナレーション: 「平時のプライバシーを守り、非常時だけ助け合いを立ち上げる。Zashikiwarashi でした。ご清聴ありがとうございました。」
