# Zashikiwarashi — 課題・ユーザー・要件定義書

*Version 1.0 / Hackathon MVP*
*マンション内の潜在的な助け合いを、緊急時だけ安全に利用可能にするMulti-Agentサービス*

> 仲良くならなくても、助け合える。
> 普段は意識しなくていい。必要なときだけ、マンション全体がセーフティネットになる。

---

## 1. 課題

### 1.1 解決すべき問題

マンションには、助けを必要としている人も、助けられる人もいる。しかしお互いのことを知らないため、その力は使われていない。

- **高齢単身世帯**: 停電でエレベーターが止まると、14階から階段で水を取りに行けない。隣室に誰が住んでいるかも分からない。
- **乳幼児世帯**: 親の帰宅が2時間遅れたとき、鍵を持たない子どもがエントランスで締め出される。面識のない住民に頭を下げて頼む心理的ハードルは高い。
- **管理人**: 地震直後に150戸の安否を1人で確認すると2〜3時間。初期救助のゴールデンタイムを逃す。

### 1.2 既存アプローチの限界

| アプローチ | 限界 |
| :--- | :--- |
| **住民LINEグループ・SNS** | 「今家にいます」「水あります」を全員が自ら発言する心理的・時間的コスト。在宅状況・移動制約などの個人情報がグループ全員に丸見え。平常時のSNS疲れで形骸化。 |
| **汎用LLMチャットボット** | 複数住民の状態を同時に把握し、多人数の交渉プロセス（Need/Capability照合・タスク分割・Human Approval）を扱えない。プライバシー制御・段階的開示の仕組みがない。 |
| **防災アプリ・ボランティアSNS** | 平常時にプロフィール入力・持ち物登録・日常の挨拶が必要。更新が止まると形骸化し、有事に使えない。 |

### 1.3 本サービスが提供する解決策

Zashikiwarashiは、住民それぞれの暮らしを理解する**Resident Agent**と、建物全体を調整する**Building Agent**を用いて、個人情報をむやみに公開せずに「誰が困っているか」「誰なら無理なく助けられるか」を見つけ、**緊急時だけ**協力体制を作る。

- 住民には、困ったときに自分に合った助けが届く安心を。
- 管理人には、一人ですべてを調整しなくてよい環境を。
- 日常SNSや近所付き合いの活性化を目的としない。

## 2. ユーザーと価値

### 2.1 保険型の価値設計

住民に求めるのは、普段から頻繁に操作することではない。許可した生活情報を安全に預け、緊急時に無理のない範囲で互助へ参加する。その代わり、自分や家族が困った時には同じ仕組みが支援候補を探してくれる。

- 助けた回数と、助けてもらえる権利を1対1で紐づけない。
- 困っている住民は、過去の貢献量に関係なく支援対象となる。
- 金銭・ポイント報酬ではなく「必要なときに互助ネットワークが働く安心」を中心価値とする。
- 支援依頼は一人へ偏らないよう、Agentが複数候補を考慮する。

### 2.2 想定ユーザーロール

| ロール | 概要 |
| :--- | :--- |
| **住民（Resident）** | マンション居住者。平時はアプリを操作する必要がない。有事に支援を受ける側（Need）にも提供する側（Capability）にもなりうる。 |
| **管理人（Admin）** | マンション管理人または管理組合の担当者。全館緊急モードの発令、進行状況の俯瞰、優先事項の指示を行う。 |

### 2.3 想定デモシナリオ（4種）

1. **大規模停電 × EV停止** — 物資の階段バケツリレー（基幹デモ）
2. **地震直後** — 150戸の一次トリアージ（安否・閉じ込め確認の分散化）
3. **交通障害 × 親の帰宅困難** — 子どもの締め出され（セルフ緊急モード ＋ Child Safety）
4. **EV一時停止 × ベビーカー外出** — 突発3分の階段サポート

## 3. 要件

### 3.1 MVPの目的

- 緊急時に、住民同士の潜在的な支援能力を安全に発見・調整できること。
- 住民が知らない相手へ直接助けを求めたり、依頼・断りの調整をする心理的負担を下げること。
- 管理人が目的・優先事項を示すと、複数Agentが具体的な協力計画へ変換できること。
- 個人情報を必要最小限しか開示しないこと。
- Agentの協議、利用情報、開示情報、本人承認の経緯を後から確認できること。

### 3.2 対象外（MVPスコープ外）

- 平常時の住民SNS、雑談、交流促進。
- 住民の嗜好・人格を学習して日常体験をパーソナライズすること。
- ユーザーの承認・拒否履歴から「協力的／非協力的」等の人物評価を作ること。
- 生命に直接関わる医療・救急・避難判断の自動決定。
- 住民本人の承認なしに実世界の支援行動を確定すること。
- 氏名、電話番号、生の移動履歴等をAgent間で無制限に共有すること。
- 本番運用レベルの本人確認、法務、責任分界の完全実装。

### 3.3 学習方針（軸の固定）

Agentが学習・更新する対象は、緊急時の状況判断に必要な「生活文脈」に限定する。ユーザーの好みを広く推定するPreference ProfileはMVPでは作らない。

- **対象**: 在宅傾向、生活時間帯、世帯構成、移動・支援に関する事実ベースの生活文脈。
- **非対象**: 性格、価値観、協力度、日常的な好みの推定。

承認・拒否などの操作履歴は監査履歴として保持できるが、人物評価には変換しない。生活文脈はユーザーが確認でき、誤りがあれば訂正可能にする。

## 4. プライバシー・セキュリティ要件

### 4.1 基本原則

- **Privacy by Default**: 明示されていない情報は利用・共有しない。
- **Least Disclosure**: 同じ目的を達成できるなら、より粗い情報粒度を選ぶ。
- **Need-to-Know Context**: LLMへ必要な情報だけ渡し、Memory Storeを丸ごとPromptへ入れない。
- **Agent Isolation**: Resident Agentは他住民のRaw Data / Memoryへ直接アクセスしない。相手のAgentへ質問する。
- **Outbound Privacy Gate**: すべてのAgent外向き通信をPrivacy Gatewayへ通す。
- **Human-in-the-Loop**: 実世界アクションと高識別情報の開示は本人承認必須。
- **Auditability**: 誰が、いつ、何を利用・公開・承認したか記録する。

### 4.2 Progressive Disclosure

情報は目的に必要な最小粒度でのみ公開する。システム側が「最大でもここまで」という公開上限を定め、その範囲内で本人が通常時・緊急時の許可を設定する。

- **抽象**: 「対応可能な住民が1名います」
- **条件**: 「同じ階付近に、現在対応可能な住民がいます」
- **識別**: 「704号室が対応可能です」— 実行に必要な場合のみ本人承認後。

氏名、電話番号、生の行動履歴は最大公開ライン外。

### 4.3 データの段階的抽象化

```
Raw Data → Lifestyle Memory → Emergency Context → Shared Context → Execution Token
```

他Agentが他住民のMemoryを直接読むことは禁止し、必要な質問を相手のResident Agentへ行う。

### 4.4 ハッカソンMVPでのセキュリティ境界

Cloud KMS、VPC Service Controls、Security Command Center等は本番拡張候補とし、ハッカソンMVPでは必須実装に含めない。保存/通信の標準暗号化はGCP側の基本機能を利用し、特に高機密なRaw Dataは論理的に分離する。

## 5. 非機能要件

- **Explainability**: 支援候補に選ばれた理由と、使用・開示した情報を説明できる。
- **Load Fairness**: 同一住民へ支援依頼が集中しないよう複数候補を考慮する。
- **Fail Safe**: LLM失敗時や会話収束しない場合は管理人/本人へ手動判断を返す。
- **Conversation Bound**: Agent間会話はMVPでは最大3〜5ラウンド程度を目安とし、収束しなければBuilding Agentが再計画する。
- **Availability**: ハッカソンでは高可用性よりデモの再現性・監査可能性を優先する。

## 6. 受け入れ基準（MVP Done）

- [ ] 管理人が建物全体を緊急モードにできる。
- [ ] 住民が自分だけ緊急モードにできる。
- [ ] 住民と部屋番号が紐付いた認証済みユーザーとして操作できる。
- [ ] 管理人が自然言語で目的を指示できる。
- [ ] 3名以上のResident Agentが異なるNeed/Capabilityを持って複数ラウンド協議できる。
- [ ] Building Agentが1対1に限定されない協力計画を生成できる。
- [ ] すべての外向きAgentメッセージがPrivacy Gatewayを通る。
- [ ] 本人未承認の実世界アクションがCommitされない。
- [ ] 管理人が全問い合わせと進行状況を確認できる。
- [ ] 住民が後から協議要約・利用情報・公開情報・承認履歴を確認できる。
- [ ] 最大公開ラインを超える個人情報がAgent間に表示されない。
- [ ] ユーザー選択から嗜好・人格プロフィールを生成しない。
