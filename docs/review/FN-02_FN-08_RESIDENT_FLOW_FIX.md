# FN-02 / FN-08 安否再回答・ペルソナ切替の調査と修正

## 確認した発生条件

| 条件 | 修正前の挙動・原因 | 修正 |
|---|---|---|
| 無事回答後に「被害ありに変更」、または被害あり回答後に更新 | 編集フォームと回答済み画面の表示条件が独立し、同時に表示される。被害あり→無事へ戻る導線もない | 編集中は待機画面を隠し、被害あり回答後は2択から再回答可能にした |
| 送信中の連打 | 安否POSTの多重実行を防ぐ仕組みがない | 同一画面で送信を直列化し、送信ボタンを無効化 |
| 保存成功後に再取得が失敗 | POST結果を画面に反映せず、再取得だけに依存しているため、旧回答が残り再回答できなかったように見える | サーバーが受け付けた回答を対象住民・住戸・集計に反映してから再取得 |
| カスタムクレームに resident_id / role があるアカウントで切替 | 選択ペルソナよりログイン情報を優先し、別住民として回答を保存。管理人集約取得が住民として処理される場合もある | Studioの定義済み5ペルソナの role / resident_id / unit_id を一組で解決。ログインuidは維持 |
| API応答が5秒以上かかる | 5秒ごとに新規取得が始まり、古い取得を捨て続けるため、回答状態が更新されない | 取得完了後に5秒待って次の取得を実行 |
| 送信完了前に住民切替・再発令 | 遅れて完了した処理が旧画面・旧災害の情報を反映し得る | 住民ごとの画面初期化を維持。回答先住民の状態だけ更新し、災害・ログインが変わった旧処理は反映しない |
| 管理人ペルソナ選択 | 住民用の安否フォームが表示される | 管理人の案内・集計画面に分岐。APIでも管理人の安否POSTを拒否 |

API単体の有効な災害へのSAFE / NEED_HELP再送は元から成功し、再回答そのものを禁止する制約はなかった。終了済み災害への回答拒否は維持した。

認証の修正前後比較では、同じGoogleログイン（クレームは住民I）で住民Hを指定した結果が、修正前 `resident-i / unit-301`、修正後 `resident-h / unit-302` となることを確認した。
