## 2. SPEC（`MURAKAMI_REVIEW_SPEC.md`）

### S-1【提案】§1.1 問題提起：「共同生活」から潜在的な課題へつなぐ流れ

対象箇所: 「マンションには、助けを必要としている人も、助けられる人もいる。しかしお互いのことを知らないため、その力は使われていない。」の直後

> マンションって共同生活ってよく言われるよね
> → マンションが共同生活と感じる場面って騒音被害とか（デメリット）？
> → マンションが共同生活たるメリットってなかなか見えない（特に単身用の賃貸とかだと）
> → AIエージェントを活用してマンションの潜在的なコミュニティを活かして助け合いできるといいね
> みたいな流れはどうだろうか
> 潜在的な課題 感を出したい

- 意図: 導入を「共同生活＝デメリットばかり意識される → メリットが見えない → 潜在的な助け合いをAIエージェントで活かす」の順にし、「潜在的な課題」であることを強調する。
- 影響: SPEC §1.1 の書き出し、および記事・提出資料のストーリー構成。

## 3. DESIGN（`MURAKAMI_REVIEW_DESIGN.md`）

### D-1【質問】§1 原則2「嗜好・人物学習の完全排除」と初回プロフィール登録

対象箇所: 「意思決定・協調計画は、空間距離、時間的空き状況、身体的制約などの『客観的事実データ』のみに基づく。」の直後

> ある程度のプロフィール情報は初回ログイン時に登録するでOK？

- 意図: 嗜好・人物プロファイリングは排除しつつ、客観属性（身体的制約など）を初回ログイン時に一度だけ登録する運用でよいか確認したい。
- 関連: DESIGN §3.2 は「入居時の初回登録1回のみ。平時の追加入力ゼロ」としており、方向性は整合していそう。登録項目とプロファイリングの線引きを明文化するかは要検討。

### D-2【質問】§3.2 想定するマンションの規模

対象箇所: Cat 2（住民・世帯の基本属性データ）の見出し直下

> ここでコメントすることかわからないけど、今回は結構でかいマンションを想定するのかな？

- 意図: 想定する建物規模（戸数）を確認したい。SPEC §1.1 には「150戸」の記述がある。

## 4. ARCHITECTURE（`MURAKAMI_REVIEW_ARCHITECTURE.md`）

### A-1【質問】概要：電力スマートメーターの利用

対象箇所: システム概要の説明文（「…電力スマートメーターからデータを収集し…」）の直後

> 電力スマートメータって使うの？

- 意図: 電力スマートメーターを本当に使うのか。使う場合のデータ取得手段と MVP での扱い。
- 関連: §2.3 で待機電力／活動電力による不在検知に使う設計。

### A-2【質問】§2.2 Google Calendar API 連携の用途

対象箇所: §2.2 見出し直下

> Google Calenderはその人が外出中かそうでないかの判断で使う？
> GPSではなく？

- 意図: Calendar を在宅／外出の判定に使うのか。判定に GPS を使わない理由を説明できるか。
- 要確認: Calendar は「予定に基づく不在見込み」、GPS などの端末シグナルは「オプトイン」という役割分担を、docs に明記するか。

### A-3【質問】§2.4 マンション集合インターホン盤連携

対象箇所: §2.4 見出し直下

> ここもMVP?

- 意図: インターホン盤連携が MVP 範囲かを確認したい。
- 関連: §2.1 の注記は「MVP の最小構成は Google Calendar 連携のみ必須」。範囲外なら §2.4 に「拡張候補」と明記するのが妥当。`docs/PLAN.md` §2 で確認。

### A-4【評価＋提案】§3.4 プライバシー & Multi-Agent 実行基盤：AI Agent のガバナンス

対象箇所: §3.4 見出し直下

評価:

> もし、Sensitve Data Protection使うのはいいね！

提案:

> 今回のハッカソンのテーマ的にAI Agent実行基盤としてのガバナンスやオブザーバビリティを実現するのがいいのかなと思った
> 例えば、AI Agentに対する入力や出力は全部Agent Gatewayを通るように設計して、Model Armorでエージェントへの入力をチェック（プロンプトインジェクション対策だったりポリシーのアタッチ）。また、AI Agentがどういう動作をしているのかはAgent Observability（OpenTelemtry?）で追跡 とか
> データに対する防護策は結構ねられている一方で、AI Agentのガバナンス的な観点は、少なくともこのドキュメントではあまり語られていない印象

- 提案内容:
  - AI Agent の入力・出力をすべて **Agent Gateway** 経由にする設計
  - **Model Armor** による入力チェック（プロンプトインジェクション対策、ポリシーのアタッチ）
  - **Agent Observability**（OpenTelemetry?）による Agent の動作追跡
- 指摘: データ保護は作り込まれている一方、AI Agent のガバナンス観点がドキュメントで弱い。

追加コメント（同節内の `児童保護ポリシー（私室連れ込み禁止、防犯ラウンジ限定）` について）:

> →この辺とかめっちゃいいけど、AI Agnetに判断とかさせるならAgent Gatewayでポリシーアタッチしてますとかの方が嬉しいかも

- 意図: 児童保護ポリシーの内容自体は高評価。ただし Agent に判断させるなら、「Agent Gateway でポリシーをアタッチして強制している」という形で示した方がよい。
- 関連: AGENTS.md の Domain Principles 4（LLM に権限を与えない／Policy Engine で強制）・6（Outbound Gate）と方向が合う。Agent Gateway の位置づけを Privacy Gateway とどう整理するかは要検討。
