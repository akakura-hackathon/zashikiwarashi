## プロジェクト概要

（200〜300文字。下の文は 278 文字）

Zashikiwarashiは、マンション内の潜在的な助け合いを、災害時だけ安全に利用可能にするMulti-Agentサービスです。平時は手入力ゼロ・人物プロファイリング禁止でプライバシーを完全秘匿し、地震や停電の発生時のみ建物全体のBuilding Agentと住民個別のResident Agentが自律協調します。Geminiが棟内の空間近接性に基づきエレベーター停止下での最適ペアリングを立案する一方、身体制約に応じた過大タスク拒絶や、本人の1タップ承認を経るまで部屋番号を開示しない段階的開示（Progressive Disclosure）をコードとModel Armorで物理強制します。

## プロジェクト紹介

### 課題と解決

**課題: マンションの「垂直孤立」。助け合いたいが、平時のプライバシーと過度な負担が壁になる**

首都直下地震や風水害時、タワーマンションや中高層住宅では**エレベーター全基停止による「垂直の陸の孤島」化**が極めて深刻です。高齢単身世帯や歩行困難者が高層階に取り残される一方、公的救助が全住戸に届くには数時間〜数日を要します。

棟内には「階段を降りられる元気な住民」「医療や介護の心得がある住民」などの潜在的な助け合いの力（共助）が存在します。しかし、従来の防災アプリや名簿には3つの大きな壁がありました：

1. **平時のプライバシー懸念。** 「平時から協力可能と登録する」仕組みだと、日常のボランティア負担やご近所付き合いの煩わしさを恐れ、誰も登録しません。
2. **人物プロファイリングへの恐怖。** 「誰が協力的か」「誰が要支援か」をスコアリングされることへの心理的抵抗。
3. **善意への過度な依存と二次災害。** 助けを求めた相手が実はケガ人や高齢者で、無理な階段昇降を頼んで共倒れになるリスク。

**解決: 平時は完全秘匿。災害時だけ 2 体の Agent が立ち上がり、個人情報を守りながら自律協調する**

Zashikiwarashi は、**「平時の手入力ゼロ」「人物プロファイリング禁止」** を大原則とします。平時は何も求めず、災害が発生した瞬間だけエージェントが立ち上がり、助け合いを安全に成立させます。

| 段階 | Zashikiwarashi（Multi-Agent）がすること | 人がすること |
|---|---|---|
| **発令** | 気象庁アラートや防災センターの災害検知で緊急モード発令。全50戸へ一斉安否配信 | 管理人がワンタップで発令（または自動） |
| **応答** | 住民スマホへスリープ復帰通知。1タップで「無事 / 支援要」を受信。困りごとは Resident Agent が対話で構造化 | 住民がスマホで1タップ回答（無事 / 救助要請） |
| **トリアージ** | **Building Coordinator Agent** が棟内空間データ（同階・隣室・EV停止）と安否未応答を解析し、近接ペアリング計画を立案 | — |
| **制約検証** | 打診を受けた **Resident Agent** が本人の身体制約（高齢・歩行困難等）を自律判定。階段作業等の過大タスクを拒絶し、同一フロア見守りへ逆提案 | — |
| **打診・承認** | **段階的開示（Progressive Disclosure）**。打診時は「3階の未応答住戸」とだけ伝え、部屋番号を秘匿 | 住民がタスク内容を見て「協力する」を1タップ承認 |
| **開示・実行** | 本人承認が完了した瞬間にのみ、相手の正確な部屋番号（例: 302号室）を開示。現地確認を実行 | 住民が隣室を確認し、結果を1タップ報告 |
| **優先救助** | 「本人未応答 × 隣室確認も応答なし」の孤立住戸を自動特定し、防災センター卓へ最優先アラート送出 | 管理人・救助隊が現地へ直接出動 |

**設計の中心: 「LLMに権限を与えない」コード強制ガバナンスと段階的開示**

命とプライバシーを扱う防災サービスだからこそ、**「AI（LLM）の善意やプロンプト指示だけに頼らない」** アーキテクチャを徹底しました。

- **段階的開示（Progressive Disclosure / G5）:** エージェント間（Agent-to-Agent）の通信では `[3F_UNIT]` などの抽象トークンのみが流通します。実世界の部屋番号は、住民本人が画面上で「協力する」と明示的に承認（Human-in-the-Loop）するまで、コードレベルで秘匿されます。
- **コード（Policy Engine）による物理遮断（G4）:** 承認の記録、部屋番号の復号、権限昇格は、LLM ではなく決定論的な Policy Engine が強制します。LLM がどれほどハルシネーションを起こしても、未承認の個人情報は漏洩しません。
- **Google Cloud Model Armor によるリアルタイム防壁（G2）:** 住民からの自由記述メッセージやエージェント間通信に対し、Model Armor テンプレート（`zashikiwarashi-guardrails`）がプロンプトインジェクションやジェイルブレイク攻撃をインフラ層でリアルタイム遮断します。
- **人物プロファイリングの完全排除:** 協力・拒否の履歴は監査ログに残すのみで、住民のスコアリングや評価値への変換はシステム上一切行いません。

### アーキテクチャ説明

**全体の構成**

```
審査員 / 防災センター卓 ── Firebase Hosting ── Studio UI（Next.js） ──┐
一般住民（スマートフォン） ───────────────────────────────────────────┤
                                                                      ▼
                                                       API Gateway (Google Cloud)
                                                                      │
                                                   ┌──────────────────┴──────────────────┐
                                                   ▼                                     ▼
                                       Cloud Run: api (FastAPI)              Cloud Run: tools (MCP)
                                       Policy Engine / 業務ロジック           空間計算・世帯プロファイル
                                                   │
                      ┌────────────────────────────┴────────────────────────────┐
                      ▼                                                         ▼
    Agent Gateway (Ingress: Model Armor 検査)                 Agent Gateway (Ingress: Model Armor 検査)
                      │                                                         │
   Vertex AI Agent Runtime: building-coordinator-agent       Vertex AI Agent Runtime: resident-agent
   (Building Coordinator Agent / Gemini 2.5 Flash)           (Resident Agent / Gemini 2.5 Flash)
   - 棟内空間近接トリアージ (50戸)                           - 身体制約保護・過大タスク拒絶
   - 階段移動最小化ペアリング立案                            - 段階的開示（承認前の部屋番号秘匿）
                      │                                                         │
                      └─────────────────── Agent-to-Agent 通信 ───────────────────┘
                                         (Privacy Gateway: 抽象トークンのみ)
                                                   │
                                                   ▼
                                       Cloud Firestore (default)
                                       50戸の安否・タスク・監査ログ
```

**技術スタック**

| 区分 | 採用したもの | 役割・選定理由 |
|---|---|---|
| **AIエージェント** | Google ADK (Agent Development Kit), Gemini 2.5 Flash, Vertex AI Reasoning Engines (Agent Runtime 2体) | Building Coordinator Agent と Resident Agent を別々のマネージドランタイムとして完全分離デプロイ |
| **エージェント統制・防壁** | Google Cloud Model Armor, Agent Gateway, Policy Engine (コード強制) | プロンプトインジェクションのインフラ層遮断、未承認ツール呼び出しの物理拒絶 |
| **アプリケーション基盤** | Cloud Run (FastAPI × 2: `api`, `tools`), Google Cloud API Gateway, Firebase Hosting | サーバーレスで堅牢なマイクロサービス構成、低レイテンシ配信 |
| **データストア** | Cloud Firestore (ネイティブモード・us-central1) | 棟内50戸の安否状況・タスク進行・監査イベントのリアルタイム永続化 |
| **可観測性・監査** | Cloud Trace, Cloud Logging (OpenTelemetry) | エージェント間の分散推論トレース（`plan_id` 伝搬）とセキュリティ監査証跡 |
| **フロントエンド** | Next.js 15 (App Router), Vanilla CSS, PWA / Studio Architecture | 防災センター卓と住民スマホを1画面で同時検証できる審査用デュアルビュー |
| **インフラ自動化** | Terraform (単一GCP環境), GitHub Actions (Workload Identity Federation) | サービスアカウントキー非発行のセキュアな自動デプロイパイプライン |

**設計上の工夫**

1. **Building と Resident を 2 つの独立した Vertex AI Agent Runtime に物理分離した。**
   棟全体の最適化を担う管理者視点の Building Agent と、住民個人の尊厳・プライバシーを守る Resident Agent を別々のランタイムにデプロイしました。Resident Agent が自立した防壁となることで、上位エージェントからの「命令」であっても、住民の身体制約に合わないタスクを自律的に拒絶・逆提案できる権力分立を実現しています。

2. **モックなしの本番 GCP 環境での稼働。**
   ハッカソン向けのプロトタイプでありながら、Vertex AI Reasoning Engines、Cloud Run、API Gateway、Firestore、Model Armor をすべて本番 GCP プロジェクト（`zashikiwarashi`）上に Terraform で構築し、実際にデプロイして稼働させています。

3. **審査員が 1 画面で全てを体験・検証できる「Studio Architecture」。**
   被災状況の全体把握（左側: 防災センター卓・全50戸 FloorMap）と、一般被災住民の心理的体験（右側: スマートフォン実機フレーム）を並列配置しました。災害発令から AI 推論、住民スマホへのタスク着信、ワンタップ承認による部屋番号開示、そして Model Armor の攻撃遮断テストまでを、認証不要の「🚀 クイックデモセッション」で即座に検証できます。

4. **マルチ災害シナリオ（地震・停電・火災・洪水）の自律推論対応。**
   基幹デモの SC-3（地震・エレベーター停止）に加え、SC-1（停電・物資階段リレー）、SC-2（火災・同フロア避難同行）、SC-4（洪水・上層階垂直避難）の 4 つの災害種別ごとに、Building Agent が異なる空間最適化ロジックと指示文を動的に切り替えて推論します。

**実装の範囲（正直に書く）**

- **対象建物データは、50戸（5階建て・各フロア10戸）の実データ構成です。**
  健常単身者（住民I: 301号室）、高齢単身者（住民H: 302号室・要配慮）、一般世帯（住民J: 303号室）、外出中（住民K: 504号室・Likely Away）など、リアリティのある世帯構成を Firestore に投入して検証しています。
- **デモ画面では、ペルソナ切り替えにより 1 人の審査員で双方の視点を操作できます。**
  本来は 50 人の住民が各自の端末で操作するものですが、審査員が 1 人で検証できるよう、左パネルのペルソナ選択により住民I・住民H・防災センターを瞬時に切り替えて操作可能です。
- **Model Armor は実機で「ブロック（物理遮断）」モードで稼働しています。**
  単なるログ記録ではなく、プロンプトインジェクション攻撃を検知した瞬間に HTTP 400 Bad Request を返し、Agent への到達を遮断する動作を実機確認しています。
- **Web Push 通知の実機連携について。**
  画面内のスリープ復帰擬似通知（`LockNotification`）は完成していますが、物理的なスマートフォン端末への FCM HTTP v1 によるバックグラウンドプッシュ通知は「余力拡張タスク」として設計済み候補に位置づけています。
- **今後の実装・拡張候補:**
  オフライン PWA キャッシュ基盤、BLE（Bluetooth Low Energy）メッシュネットワークによる全館完全通信断時のピアツーピア安否リレー、スマートロック（Bitkey 等）API 連携による緊急時解錠委任。
